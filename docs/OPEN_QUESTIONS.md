# Открытые вопросы и расхождения — черновик v0

Собрано агентами при написании фрагментов (2026-09-25/26) из кода `club-shell`. Часть расхождений уже
исправлена на этапе проверки; вопросы ниже — к владельцу и ко второй стороне. Ссылки — от корня `club-shell`.

## Проверено вручную

1. **501 повторяется агентом и бьёт по circuit breaker.** `RetryPolicy.IsTransient` считает любой статус ≥ 500
   временным (`src/ClubShell.Core/Http/RetryPolicy.cs:55`); идемпотентные запросы (GET/PUT/DELETE и POST с
   `Idempotency-Key`) повторяются до `MaxAttempts = 5` (`AppSettings.cs:242`), каждая попытка идёт через общий
   circuit breaker (`RetryPolicy.cs:113-120`, `FailureRatio 0.8`). Правило «отдаём 501 вместо заглушек» безопасно
   только для вызовов, которые агент не делает сам.
2. **Повторы Polly несут ту же подпись.** Подпись ставится один раз в `ServerClient.Authorize`
   (`ServerClient.cs:774`, `825-832`), повторы идут внутри `HttpClient` (`RetryPolicy.cs:155`). Защита от повторов
   по `(pcId, X-Timestamp, X-Signature)` отклонит каждую повторную попытку.

## Вопросы по группам

### base

- 501 has no suitable ErrorCode. ErrorCode.cs:14-75 has no notImplemented value. CamelCaseEnumConverter (JsonDefaults.cs:113-121) has no fallback for unknown values, so a code like 'notImplemented' throws JsonException. ServerClient.ReadErrorAsync (ServerClient.cs:589-610) then drops the whole envelope and falls back to ErrorCodes.FromHttpStatus(501) = serverUnavailable (ErrorCode.cs:148), losing message and details. Interim choice in NotImplemented: error.code = serverUnavailable with details.reason = notImplemented. The owner should confirm this, or add ErrorCode.NotImplemented, which only works after an agent release.
- 501 on notImplemented operations can disconnect the agent from the server. RetryPolicy.IsTransient (RetryPolicy.cs:55) treats every status >= 500, 501 included, as transient. GET/PUT/DELETE and POSTs with Idempotency-Key are retried up to MaxAttempts=5 (AppSettings.cs:242) with 0.5-15 s backoff. Every attempt counts toward one circuit breaker shared by all requests of the named client (RetryPolicy.cs:112-120: FailureRatio 0.8, MinimumThroughput = max(2, Failures=5) = 5, window and break 30 s, AppSettings.cs:258-262). So one call to a notImplemented GET produces 5 failures in about 8 s and opens the circuit for 30 s. During that time heartbeat, sessions and auth all fail with serverUnavailable. The agent makes such calls routinely: GET /apps (GameHandlers.cs:98; with an empty cache, apps.list fails outright), GET /shop/products (SessionHandlers.cs:714), GET /wallet/{userId}/balance (SessionHandlers.cs:643), and the periodic GET /updates/{channel}/manifest (UpdateChecker.cs:170). Options: (a) change the agent to exclude 501 from IsTransient and from the circuit breaker; (b) answer notImplemented operations with a non-5xx status (for example 404 notFound or 403 policyDenied with rule=notImplemented); (c) give v1 minimal stubs for the operations the agent polls: empty lists for /apps, /shop/products and /pcs, and 204 for /updates/{channel}/manifest. I did not change any statuses.
- Replay protection conflicts with how the agent retries. ServerClient.Authorize computes X-Timestamp and X-Signature once per SendOnceAsync, before _http.SendAsync (ServerClient.cs:774, 825-832). The Polly retries in RetryPolicy.cs:95-109 run inside the HttpClient pipeline and resend the same headers. Separately, two identical requests in the same second get the same signature, because the timestamp is whole Unix seconds (Signing.cs:76-92). Strict tuple uniqueness (SERVER_API.md:64) would turn every such retry into a 401. The agent answers any 401 reason other than clockSkew/userToken with a refresh (ServerClient.cs:725-730), which rotates the one-time refresh token, and a retried idempotent POST would never reach the idempotency replay. The owner needs to decide how. For example: record the tuple only after a final non-5xx response, exempt requests that carry an Idempotency-Key, or narrow what counts as a replay.
- x-prohibited: telegram fields in responses. apps/admin declares telegram: string as non-optional in Client (api.ts:437) and calls .trim() on it (ClientsPage.tsx:80, 123). notifications.telegramBotToken and telegramChatId are also non-optional (api.ts:286-287). If the server leaves these fields out, saving a client in the cashier UI throws a TypeError. My proposed rule in info §10 is to accept and ignore these fields on input and to return an empty value of the same type rather than omit them. The owner should confirm.
- 426 versionMismatch for REST is not defined. VersionMismatchDetails { supported: int[], got: int } (IpcErrors.cs:190-193) describes IPC protocol majors, while REST sends semver strings in X-Agent-Version/X-Shell-Version (ServerClient.cs:750-751). Nothing says which versions get a 426 or what goes into details. There is also a deadlock: ARCHITECTURE.md:394 allows 426, but GET /updates/{channel}/manifest is notImplemented, so a rejected agent cannot update itself. My proposal is that server v1 does not return 426 until updates are implemented.
- Compatibility of enum values. Adding fields is safe, since UnmappedMemberHandling.Skip is set at JsonDefaults.cs:94. A new enum value is not: CamelCaseEnumConverter has no fallback (JsonDefaults.cs:113-121), so the whole response fails with ProtocolError 'Malformed response body' (ServerClient.cs:632-635), or the error envelope is dropped. Info §9 records this as a breaking change. The owner should confirm the policy: new enum values only with an agent release, or only in /api/v2.
- Extra components I added, beyond the list in the task. IdempotencyKeyOptional (required: false) is for create/charge POSTs whose client does not send the key; apps/admin never sends Idempotency-Key (api.ts:89-97). IdempotencyKey itself is required: true because the agent always sends it on those POSTs. The admin group should confirm it will use IdempotencyKeyOptional for /admin/* POSTs. IdempotentReplayed is the response header 'Idempotent-Replayed: true' from mock db.ts:488. count=34 is the number of components (4 securitySchemes, 13 parameters, 5 headers, 12 responses); there are 0 operations and 0 schemas. bundle.py currently fails only on the expected dangling $ref #/components/schemas/ServerErrorEnvelope, which another group owns.

### schemas-pc

- A 501 from any notImplemented operation that the agent still calls will be retried and counted by the circuit breaker, which can block heartbeats and sessions for 30 s. Evidence: RetryPolicy.IsTransient treats status >= 500 as transient (src/ClubShell.Core/Http/RetryPolicy.cs:54). GETs and POSTs with an Idempotency-Key are retried up to 5 attempts (:94-108). The shared breaker 'clubshell-server' (FailureRatio 0.8, MinimumThroughput 5, 30 s window and break; RetryPolicy.cs:112-119 and :155) counts every 501. One GET that gets 501 is 5 failed attempts, which can open the breaker for 30 s. The README claim 'the agent does not retry 4xx' does not help here, because 501 is a 5xx. Conclusion: in normal operation the server v1 must not let the agent reach any 501. That is done with features (see x-feature-gates) and config switches; the operations listed below cannot be switched off that way.
- GET /pcs/{pcId} is marked notImplemented, but the agent calls it for sys.pcInfo on every Shell start. The 60 s cache applies only on success (src/ClubShell.Agent/Ipc/Handlers/SystemHandlers.cs:433-450), and no feature flag hides it. I propose making it required: it is trivial and returns the Pc record the server already has from register/heartbeat.
- GET /wallet/{userId}/balance and /transactions are notImplemented. The Shell's /wallet route has no feature gate (apps/shell/src/router.tsx:434), the balance is shown in the HUD (apps/shell/src/screens/Desktop/HudBars.tsx:397), and the agent calls the endpoints (src/ClubShell.Agent/Ipc/Handlers/SessionHandlers.cs:643, :679). ShellFeatures has no flag to hide them. I propose making balance (and preferably transactions) required.
- GET /updates/{channel}/manifest is notImplemented. UpdateChecker polls it every updates.checkIntervalSec (src/ClubShell.Core/Updates/UpdateChecker.cs:148, :170). The server can only raise the interval to 604800 (AppSettings.cs:562) and cannot turn polling off. I propose making it required and always answering 204 ('up to date').
- POST /anticheat/report is notImplemented. It can only be disabled locally in agent.json (anticheat.reportViolations, src/ClubShell.Agent/AntiCheat/AntiCheatMonitor.cs:354), because AgentServerConfig has no anticheat section (SettingsLoader.cs:163-194). Should it be required (accept and return 204), or should the anticheat section be added to the config?
- Please confirm that server v1 will always send the following in AgentServerConfig. games.accountPool.enabled=false and games.cloudSave.enabled=false, because /games/{id}/accounts/* are notImplemented and both default to true in agent.default.json:60-61; gating is in GameLaunchService.cs:204 and CloudSaveSync.cs:51. shell.features with shop, chat, booking, tournaments, topup, apps and callAdmin set to false, while profile can stay true since /users/* is required. The feature-to-operation map in x-feature-gates is built from the Shell screens (router.tsx:427-453, NavBar.tsx:33-38, SupportScreen.tsx:302-337, HudBars.tsx:381-397, DesktopScreen.tsx:411-413); the owners of the paths fragments should check it.
- AgentServerConfig.themes is ignored by the agent (there is no downloader), so shell.theme should be limited to themes shipped with the Shell (config/themes: default, neon) until downloading exists. Should the contract write this down as an enum or a recommendation?
- Enabling storage.gamesShare.enabled from the server takes effect only after the agent service restarts: GamesShareMounter.StartAsync checks the flag once (src/ClubShell.Agent/Storage/GamesShareMounter.cs:78-90). Is that acceptable for the product, or does the server need a restart command after changing storage?

### schemas-commands

- POST /support/call-admin помечен notImplemented, из-за этого кнопка «Вызвать администратора» в v1 работает только через телеметрию. Что происходит у агента (src/ClubShell.Agent/Ipc/Handlers/SystemHandlers.cs:212-256): 501 приходит как serverUnavailable с IsRetryable = true; POST с Idempotency-Key повторяется до 5 раз (RetryPolicy.cs:98-110, AppSettings.cs:242), и каждая попытка идёт в общий circuit breaker. После этого тикет уходит событием телеметрии kind = callAdmin (data = CallAdminTicketRequest), а шелл получает фиктивный ticketId. Варианты: сделать операцию required; или обязать сервер v1 разбирать TelemetryEvent kind = callAdmin из POST /agents/{pcId}/telemetry (required) и уведомлять кассу; или выключать кнопку через config features.callAdmin (SystemHandlers.cs:214).
- GET /updates/{channel}/manifest (схема UpdateManifest) помечен notImplemented. UpdateChecker (src/ClubShell.Core/Updates/UpdateChecker.cs:148,170) проверяет обновления для agent и shell каждые updates.checkIntervalSec (по умолчанию 3600 с, минимум 60). Каждый 501 — это до 5 попыток GET (RetryPolicy.cs:42-55), и все они считаются общим circuit breaker'ом: FailureRatio 0.8, MinimumThroughput 5, окно и размыкание по 30 с (RetryPolicy.cs:112-119, AppSettings.cs:258,262). Значит, одна проверка может разомкнуть цепь на 30 с для всех запросов агента, включая heartbeat. Предлагаю в v1 реализовать минимальную версию: всегда отвечать 204 «обновлений нет». Агент это штатно обрабатывает (UpdateChecker.cs:177).
- Совместимость ServerCommandType вперёд. Новое имя команды, которого нет в enum старого агента, в REST-ответе GET /agents/{pcId}/commands ломает разбор всей пачки (Heartbeat.cs:267 → ServerClient.cs:634, protocolError), и ни одна команда из неё не выполнится. По WS такое имя даёт ack notFound (RealtimeClient.cs:379), и это безопасно. Нужно ли правило: новые типы команд отдавать только агентам с подходящей X-Agent-Version?
- Нужен ли серверу лимит на число событий в TelemetryBatch? Агент копит до 1024 и никогда не делит пачку (TelemetryReporter.cs:96, :286). При лимите ниже 1024 (у мока 1000) выгрузка телеметрии навсегда встаёт на 400. В схеме стоит maxItems 1024.
- WS-события агента (AgentEventType) — best-effort: офлайн они отбрасываются (DependencyInjection.cs:472-492), а sessionStarted/sessionEnded/gameLaunched/gameExited агент не шлёт совсем. Подтвердить, что сервер v1 не опирается на них для биллинга и статуса и берёт данные из REST (/sessions/{id}/events, /games/{id}/launch-report, heartbeat).

### paths-agents

- GET /updates/{channel}/manifest = notImplemented is dangerous for the whole agent. UpdateChecker.CheckOnceAsync (UpdateChecker.cs:132-137) checks agent and then shell, one after the other, at startup (AgentUpdater.cs:97) and every updates.checkIntervalSec. With the default MaxAttempts=5 (AppSettings.cs:242), a GET that gets 501 is retried by Polly up to 5 times (RetryPolicy.cs:55, 66, 104-108), and every attempt counts toward the shared circuit breaker (RetryPolicy.cs:112-120: FailureRatio 0.8, MinimumThroughput 5, window 30 s, AppSettings.cs:258/262). That makes about 10 failures in ~15 s against 0-1 heartbeats, so the circuit opens for 30 s for ALL agent requests (heartbeat, sessions, auth). Suggestion: status required with a trivial implementation, i.e. always answer 204 No Content ('up to date'). This is exactly what the agent expects (ServerClient.cs:646-653, UpdateChecker.cs:179).
- GET /pcs/{pcId} = notImplemented: the shell calls IPC sys.pcInfo at startup (apps/shell/src/store/settings.ts:137-139), and the agent calls GET /pcs/{pcId} (SystemHandlers.cs:197, 433-449). A 501 means up to 5 GET attempts (a few seconds of shell startup latency) plus the same circuit-breaker risk. A failure is not cached (SystemHandlers.cs:450-453), so every sys.pcInfo call goes to the server again. The implementation is trivial (this is the same Pc as in AgentRegisterResponse.pc), so I suggest making it required.
- POST /support/call-admin = notImplemented: the agent always sends Idempotency-Key, so a 501 is retried 5 times (RetryPolicy.cs:71) and adds 5 circuit-breaker failures. The kiosk user waits several seconds, then the agent falls back and puts the ticket into telemetry as an event with kind='callAdmin' and data=CallAdminTicketRequest (SystemHandlers.cs:246-256). If call-admin stays notImplemented, then POST /agents/{pcId}/telemetry (required) must treat events with kind='callAdmin' as admin-call tickets, or these calls are lost. The alternative is to make call-admin required. This is the 'Call admin' button on the lock screen and the support screen (apps/shell LockScreen.tsx:656, CallAdminButton.tsx:91).
- POST /anticheat/report = notImplemented: the agent does not retry (no Idempotency-Key), but every violation adds one circuit-breaker failure and is lost over REST (AntiCheatMonitor.cs:359-366). The same body goes out as the WS event anticheatViolation (AntiCheatMonitor.cs:347), so the data survives only if the server handles it on WS (AsyncAPI). Please confirm that is acceptable for v1.
- Heartbeat for a deleted PC: the contract has 404 per the document, but the agent does not re-register on 404 (Heartbeat.cs:152). It would be better for the server to reject the agent token of a deleted PC with 401 reason=revoked, as the mock does. Then the WS reconnect / refresh leads to re-registration (ServerConnection.cs:284-316). Which behaviour should be normative?
- Inconsistent x-source format: base.yaml uses the prefix 'club-shell/…' (for example club-shell/docs/SERVER_API.md:10), while the fragments (schemas-*.yaml and mine) use paths from the club-shell root without a prefix (src/…, docs/…, tools/…). One style should be chosen for tooling.

### paths-catalog-commerce

- Статус GET /wallet/{userId}/balance и GET /shop/orders (оба notImplemented). Шелл при каждом входе пользователя вызывает wallet.balance (apps/shell/src/store/index.ts:44 -> store/wallet.ts:74 -> SessionHandlers.cs:643 -> ServerClient.cs:388) и shop.orders (store/index.ts:47 -> SessionHandlers.cs:789), причём для shop.orders агент features.shop не проверяет.
